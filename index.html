Type → table. Property → column. Returned row → object. The Items DbSet name supplies the table-name convention here. A DbSet<Item> is a query entry point, not a list that already contains every stored row.

EF builds mapping metadata from the model and configuration. Creating the model does not check or change our existing database schema. It must match the prepared table.

How does EF Core know which table and columns to use?

EF Core uses naming conventions unless we configure a different mapping. In this example:

  • DbSet<Item> Items exposes the Item entity type. The property name Items supplies the table name.
  • The entity properties Id and Name map to columns with those same names.
  • The class can be named Item while the table is named Items. EF Core is using the DbSet property name here; it is not automatically pluralising the class name.

For this activity, preserve the names Items, Id and Name so the default mapping matches the prepared SQL table. Renaming something in C# alone does not rename it in SQL Server.

Different names are allowed when we configure them explicitly, using [Table] and [Column] attributes, or ToTable() and HasColumnName() in the context configuration.

EF Core builds this mapping from our code and configuration. It does not automatically inspect the existing database and discover which table or column we intended.

ORM is the approach; EF Core is the framework

Object: an Item instance in C#. Relational: a row in the SQL Server table. Mapping: the correspondence between their properties and columns. EF Core implements this approach; SQL Server still executes the SQL.

Who writes the row-to-property assignments?

Compare the same report after the connection or context has been configured. The EF model and configuration still exist in other files.

ADO.NET comparison · connection is already open
using var command = new SqlCommand(
    "SELECT Id, Name FROM dbo.Items ORDER BY Name;", connection);
using var reader = await command.ExecuteReaderAsync();
List<Item> items = new();
while (await reader.ReadAsync())
{
    Item item = new Item();
    item.Id = reader.GetInt32(0);
    item.Name = reader.GetString(1);
    items.Add(item);
}

You create the command, advance the reader, choose getters, create objects and assign properties.

EF Core comparison · context and entity mapping are already configured 
var query = db.Items.OrderBy(item => item.Name);
List<Item> items = await query.ToListAsync();

The model tells EF Core how Items, Id and Name correspond to the entity. The awaited query returns a list of mapped objects. The shorter query relies on that preparation.

TWO STARTING POINTS

Which side drives the database structure?

Both approaches use EF Core entities, a DbContext and queries. The difference is how the model and database schema are established and kept in step.

Question Database First Code First
What drives the structure? The database schema. The EF Core model in code.
Common tool Reverse engineering generates entity classes and a context from the schema. Migrations describe schema changes based on model changes.
When structure changes Update the database through the agreed process, then update or regenerate the mapping. Change the model, create and review a migration, then apply it through the agreed process.
Reading data afterwards Both can use the same db.Items.OrderBy(...).ToListAsync() query.

A new application often starts with Code First. An existing database often favours Database First. These are common starting patterns, not a rule based only on database age: Code First can also be adopted for an existing database with careful setup.

Where this lecture starts

Our starting point is the prepared Inventory database. We write the tiny Item mapping by hand so you can understand it. That is an existing-database exercise, not an automatic reverse-engineering exercise. Scaffolding can generate the mapping; migrations can manage a schema from code. Today we explain both routes and run the query.

One solution contains three projects

A ProjectReference makes another project available to the build. A using directive lets this C# file use names from a namespace. They have different jobs. A NuGet package, such as the EF Core SQL Server provider, is an external dependency rather than one of our three projects.

Understand DataAnnotations before copying them

System.ComponentModel.DataAnnotations is a .NET namespace containing attribute classes. In our model, RequiredAttribute and StringLengthAttribute describe Name. C# allows the short forms [Required] and [StringLength(100)]. Validation frameworks can also use these attributes, but this Console app does not call an automatic input validator.

[Required] Mark Name as required in the EF model. For a relational schema this means a non-nullable column.
[StringLength(100)] Give the model a maximum string length of 100; the SQL Server mapping corresponds to nvarchar(100).
A key identifies the entity

By convention, EF Core recognises Id (or ItemId) as the primary key. You do not need a [Key] attribute here. SQL Server’s identity column generates IDs for new rows; today we only read the IDs already stored.

Mapping rules and input validation are different

EF Core reads these attributes as model metadata. They do not automatically reject an assignment in C#, validate every value before saving, or alter our existing table. NOT NULL also does not mean “non-empty text”. An application needs its own input validation; the database enforces its actual schema. With nullable reference types enabled, string is already required by convention; we retain [Required] to make the book’s intent visible.

Code What it does and why
db.Items Start a query for Item entities in the context.
OrderBy(item => item.Name) Ask for ascending title order. Read the arrow as “for each item, use its Name as the sort key”. item is a local parameter name, not a table name.
var query = ... Store the query definition. This line does not fetch rows.
await query.ToListAsync() Execute the query using the configured provider, wait without blocking the thread during database I/O, and collect results as List<Item>.
List<Item> items Hold the returned Item objects in a C# list.
foreach (Item item in items) Visit each already loaded object in the list; this loop does not send another query.
$"{item.Id} | {item.Name}" String interpolation: place the object’s values into the output text.
items.Count Read the number of objects in this list; it is not another database count query.
One real awaited operation

Top-level statements let you write await without an explicit Main method. Async does not guarantee faster SQL and does not mean parallel queries. Await one operation before starting another on the same context.

ToQueryString() creates a debugging representation of the generated SQL. It does not fetch rows. It is not a record of an executed command, and its text is not guaranteed to be directly executable. Alias names and formatting may vary.
